تاریخچه#

زمینه شکل‌گیری#

روش‌های دسترسی به داده
با گسترش پایگاه‌های داده‌ی رابطه‌ای در دهه‌ی ۱۹۷۰، روش‌های مختلفی برای دسترسی برنامه‌ها به داده‌ها وجود داشت. هر سیستم ممکن بود از زبان یا رابط اختصاصی خود برای دسترسی به داده‌ها استفاده کند. برای مثال:

  • استفاده از زبان SQL که در پروژه‌ی System R شرکت IBM توسعه یافت.
  • استفاده از زبان QUEL در پروژه‌ی Ingres.
  • استفاده از دستورات و کتابخانه‌های اختصاصی در dBASE .

در نتیجه، برنامه‌ای که مثلا برای dBASE نوشته می‌شد، برای کار با یک پایگاه‌داده‌ی دیگر به تغییرات و پیاده‌سازی مجدد نیاز داشت. زبان SQL هم با هدف استانداردسازی زبان پرس‌وجو معرفی شد، اما با این حال، تفاوت‌های قابل توجهی در پیاده‌سازی آن میان DBMSهای مختلف باقی ماند.

ظهور Embedded SQL
از آنجا که SQL یک زبان مستقل از زبان‌های برنامه‌نویسی بود، برای استفاده از دستورات SQL در برنامه‌هایی که با زبان‌هایی مانند C و FORTRAN نوشته می‌شدند، روشی به نام Embedded SQL شکل گرفت و در سال 1989 استاندارد شد. در این روش، دستورات SQL مستقیما در کد منبع برنامه قرار می‌گرفتند.

از آنجا که کامپایلر دستورات Embedded SQL را نمی‌شناخت، ابزاری به نام Precompiler پیش از کامپایل اصلی اجرا می‌شد. این ابزار دستورات SQL را شناسایی و کد لازم برای فراخوانی توابع کتابخانه‌ی DBMS را تولید می‌کرد. سپس کد تبدیل‌شده در اختیار کامپایلر زبان برنامه‌نویسی قرار می‌گرفت تا کامپایل شود.

در روش Static SQL، دستورات SQL از پیش در کد منبع برنامه تعریف می‌شدند. بنابراین، اگر نیاز به تغییر ساختار این دستورات وجود داشت، باید کد منبع تغییر می‌کرد و فرایند کامپایل مجددا انجام می‌شد. برای رفع این محدودیت، مفهوم Dynamic SQL توسعه یافت. در این روش، دستورات SQL می‌توانستند به‌صورت متن در زمان اجرای برنامه ساخته و برای اجرا به DBMS ارسال شوند.

🔔 اما همچنان مشکل پابرجا بود. روش پیاده‌سازی و رابط‌های برنامه‌نویسی DBMSهای مختلف همچنان متفاوت بود. در نتیجه، برنامه‌ای که برای ارتباط با یک DBMS نوشته می‌شد، لزوما نمی‌توانست بدون تغییر با DBMS دیگری کار کند.

ناهمگونی در محیط Client-Server

برخلاف محیط Mainframe که معمولا سخت‌افزارها و نرم‌افزارهای یک تولیدکننده را به کار می‌گرفتند، در محیط ریزکامپیوترها (Microcomputers) تنوع سیستم‌عامل‌ها، شبکه‌ها و پایگاه‌های داده بیشتر بود. این تنوع باعث شد مشکلاتی که پیش‌تر به آن‌ها اشاره کردم، در محیط Client-Server ابعاد گسترده‌تری پیدا کند. برنامه‌ها علاوه بر وابستگی به رابط اختصاصی DBMS، با تفاوت‌های محیط اجرایی و زیرساخت ارتباطی نیز مواجه بودند.

این شرایط نیاز به روشی استاندارد برای دسترسی برنامه‌ها به منابع داده‌ی مختلف، مستقل از DBMS و محیط اجرایی آن‌ها را، بیش از پیش آشکار کرد.

🔔 مساله این بود که چگونه یک برنامه بدون وابستگی شدید به یک DBMS خاص، بتواند با منابع داده‌ی مختلف کار کند.

روند تاریخی#

در همین راستا، شرکت‌هایی مانند Microsoft و Lotus تلاش‌هایی را برای یکپارچه‌سازی روش‌های دسترسی به داده آغاز کردند. مایکروسافت نیز فناوری Jet را به‌عنوان یک موتور پایگاه‌داده‌ی مشترک توسعه داد که امکان دسترسی به منابع داده‌ی مختلف را از طریق یک رابط یکپارچه فراهم می‌کرد. این تلاش‌ها در ادامه و با مشارکت شرکت‌های مختلف، زمینه‌ساز شکل‌گیری استانداردهایی مانند CLI و ODBC شدند.

  • اواخر دهه‌ی 80: گروه SQL Access Group (SAG) با هدف استانداردسازی دسترسی به پایگاه‌های داده و بهبود قابلیت همکاری میان سیستم‌های مختلف شکل گرفت.
  • 1990: طرحی با عنوان SQL Connectivity که توسط Microsoft، Lotus، DEC و Sybase توسعه یافته بود، به این گروه ارائه شد و مبنایی برای توسعه‌ی رابط استاندارد Call Level Interface (CLI) قرار گرفت؛ رابطی که دسترسی به پایگاه داده را از طریق فراخوانی توابع استاندارد میسر می‌کرد.
  • 1992: مایکروسافت نسخه‌ی 1.0 از ODBC را منتشر کرد. ODBC با تلاش‌های SQL Access Group در زمینه‌ی CLI ارتباط داشت، اما مشخصات و قابلیت‌های اختصاصی خود را نیز داشت.
  • 1993: فرایند استانداردسازی CLI در چارچوب استاندارد ISO/IEC 9075-3 آغاز شد.
  • 1994: نسخه‌ی 2.0 از ODBC منتشر شد و پس از آن نسخه‌ی 2.5 عرضه شد.
  • 1995: نسخه‌ی 3.0 از ODBC منتشر شد. همچنین استاندارد SQL/CLI با شناسه‌ی ISO/IEC 9075-3:1995 به‌عنوان بخشی از استاندارد بین‌المللی SQL منتشر شد.
  • 1997: نسخه 3.5 با پشتیبانی از Unicode عرضه شد.
  • 2009: نسخه‌ی ODBC 3.8 با قابلیت‌هایی مانند اجرای ناهمگام عملیات اتصال و پشتیبانی از پارامترهای خروجی جریانی معرفی شد.
  • 2016: مایکروسافت توسعه‌ی مشخصات ODBC 4.0 را با هدف گسترش پشتیبانی از منابع داده‌ی مدرن، از جمله پایگاه‌های داده‌ی سندگرا (Document-oriented) و سایر منابع غیررابطه‌ای (NoSQL) مطرح کرد. ( github )

تعریف ODBC#

ODBC مخفف Open Database Connectivity و به معنای اتصال باز (آزاد) به دیتابیس است. ODBC یک استاندارد و API1 مبتنی بر زبان C است که به برنامه‌ها اجازه می‌دهد بدون نیاز به استفاده از روش اتصال اختصاصی هر منبع داده، بدون کامپایل مجدد برنامه و از طریق Driver مربوطه، به آن‌ها متصل شوند.

🔔 هدف اصلی‌ ODBC اتصال به پایگاه‌های داده رابطه‌ای بوده و همچنان هم هست. با این حال برخلاف نام آن که به Database اشاره می‌کند، ODBC امکان دسترسی به منابع داده‌ی دیگری مانند فایل‌های Excel و CSV را نیز فراهم می‌کند منابعی که لزوما از نظر فنی پایگاه داده محسوب نمی‌شوند. به همین دلیل، من از اصطلاح منبع داده (Data Source) استفاده می‌کنم.

مزایای ODBC#

  1. قابلیت اتصال به DBMSهای مختلف: امکان استفاده از یک برنامه برای اتصال به سیستم‌های مدیریت پایگاه‌داده‌ی متفاوت، بدون نیاز به پیاده‌سازی مجزای رابط اتصال برای هر DBMS.

  2. دسترسی هم‌زمان به چند منبع داده: امکان برقراری ارتباط با چند منبع داده، حتی از DBMSهای متفاوت، در یک برنامه.

  3. قابلیت توسعه‌پذیری: امکان افزودن درایورهای جدید برای پشتیبانی از منابع داده‌ی بیشتر، بدون نیاز به تغییر یا کامپایل مجدد برنامه؛ مشروط بر اینکه برنامه از قابلیت‌های موردنیاز پشتیبانی کند.

⚠️ استفاده از ODBC به معنای سازگاری کامل با تمام DBMSها نیست!

ODBC رابط دسترسی به داده را استاندارد می‌کند، اما تفاوت‌های میان DBMSها در زبان SQL، انواع داده و قابلیت‌های اختصاصی همچنان باقی می‌مانند. بنابراین، ممکن است برای انتقال یک برنامه از یک DBMS به DBMS دیگر، تغییراتی در کد برنامه لازم باشد.

کاربردهای ODBC#

برخی از کاربردهای رایج ODBC عبارت‌اند از:

  • Excel: اتصال به پایگاه‌داده‌هایی مانند SQL Server، Oracle و MySQL.
  • گزارش‌گیری و هوش تجاری: اتصال ابزارهایی مانند Power BI و Tableau به منابع داده.
  • برنامه‌نویسی: دسترسی برنامه‌های نوشته‌شده با زبان‌هایی مانند C، Python و R به پایگاه‌داده‌ها.
  • ارتباط بین پایگاه‌داده‌ها: اتصال سیستم‌هایی مانند SQL Server و Oracle از طریق ODBC و قابلیت‌هایی مانند Linked Server.
  • پایگاه‌داده‌های میزبانی‌شده: اتصال نرم‌افزارهای محلی به پایگاه‌داده‌های موجود روی هاست، مانند MySQL.

به‌طور کلی، هر نرم‌افزاری که از رابط ODBC پشتیبانی کند، می‌تواند با استفاده از درایور مناسب به منابع داده‌ی سازگار متصل شود.

توابع استاندارد (API Functions)#

توابع استاندارد ODBC (ODBC API Functions) مجموعه‌ای از توابع هستند که به برنامه‌ها امکان می‌دهند عملیات مختلفی مانند برقراری ارتباط با Data Source، اجرای دستورات SQL، دریافت نتایج و مدیریت تراکنش‌ها را انجام دهند.

این توابع به‌صورت یک API مبتنی بر زبان C تعریف شده‌اند و به برنامه‌ها اجازه می‌دهند بدون نیاز به استفاده از API اختصاصی هر DBMS، از طریق یک رابط استاندارد با منابع داده ارتباط برقرار کنند.

🔔 تمام توابع ODBC الزاما در هر برنامه‌ای استفاده نمی‌شوند. انتخاب توابع به نوع عملیات موردنیاز برنامه بستگی دارد. همچنین میزان پشتیبانی از قابلیت‌های ODBC ممکن است در Driverهای مختلف متفاوت باشد.

نام بیشتر این توابع با پیشوند SQL شروع می‌شود و بر اساس کاربرد، شامل گروه‌های زیر هستند:

گروه نمونه توابع کاربرد
مدیریت اتصال Connection Management SQLConnect، SQLDisconnect برقراری و قطع ارتباط
مدیریت منابع Handle Management SQLAllocHandle، SQLFreeHandle ایجاد و آزادسازی Handle
اجرای دستورات SQL Statement Execution SQLPrepare، SQLExecute، SQLExecDirect آماده‌سازی و اجرای دستورات
دریافت نتایج Result Retrieval SQLFetch، SQLGetData دریافت اطلاعات حاصل از Query
اطلاعات ساختاری Metadata SQLTables، SQLColumns دریافت اطلاعات ساختار Data Source
مدیریت تراکنش Transaction Management SQLEndTran اجرای Commit و Rollback
مدیریت خطا Diagnostics SQLGetDiagRec دریافت اطلاعات خطا و هشدارها

مستندات رسمی مایکروسافت شامل دسته‌بندی توابع، شرح عملکرد، پارامترها و مثال‌های برنامه‌نویسی است: ODBC API Reference

معماری ODBC از چهار جز اصلی تشکیل شده است:

Application #

برنامه‌ای که با استفاده از توابع استاندارد ODBC، عملیات موردنیاز خود را روی منبع داده انجام می‌دهد و نتایج را دریافت می‌کند. این برنامه می‌تواند نرم‌افزاری مانند Excel، برنامه‌ای نوشته‌شده با زبان C#، ابزارهای گزارش‌گیری و تحلیل داده و … باشد.

Driver Manager #

لایه‌ای واسط میان برنامه‌ی کاربردی و درایورهای ODBC که وظایف زیر را بر عهده دارد:

  • بارگذاری و مدیریت درایورهای ODBC.
  • دریافت فراخوانی‌های ODBC از برنامه و هدایت آن‌ها به درایور مناسب.
  • استفاده از اطلاعات DSN برای شناسایی منبع داده و درایور مربوطه.

ODBC Driver #

ماژول نرم‌افزاری اختصاصی هر منبع داده که رابط استاندارد ODBC را برای آن منبع فراهم می‌کند. درایور درخواست‌های ODBC را دریافت می‌کند، آن‌ها را به شیوه‌ی قابل فهم برای منبع داده اجرا می‌کند و نتایج را در قالب مورد انتظار ODBC به برنامه بازمی‌گرداند.

درایورها به‌صورت کتابخانه‌های نرم‌افزاری در سیستم‌عامل نصب می‌شوند و Driver Manager در زمان اجرا آن‌ها را بارگذاری می‌کند. برای مثال، در ویندوز این کتابخانه‌ها معمولا از نوع DLL2 هستند.

از نظر نحوه‌ی پردازش داده، درایورها را می‌توان به دو گروه اصلی تقسیم کرد:

  • File-Based Driver: درایور علاوه بر فراهم کردن رابط ODBC، خودش وظیفه‌ی پردازش و مدیریت داده‌ها را نیز بر عهده دارد؛ مانند برخی درایورهای dBASE.
  • DBMS-Based Driver: درایور درخواست‌ها را به سیستم مدیریت پایگاه‌داده (DBMS) منتقل می‌کند تا توسط موتور آن پردازش شوند؛ مانند درایورهای Oracle و SQL Server.

🔔 استاندارد ODBC مشخص می‌کند درایورها باید چه APIها و قراردادهایی را برای ارتباط با برنامه‌های کاربردی فراهم کنند. شرکت‌های مختلف براساس این استاندارد، درایورهای مخصوص منابع داده‌ی خود را توسعه می‌دهند.
معمولا تولیدکنندگان DBMS نیز ODBC Driver مخصوص محصول خود را ارائه می‌کنند. برای مثال جهت اتصال به SQL Server از طریق ODBC باید ODBC Driver for SQL Server نصب شود.

Data Source#

منبعی است که برنامه‌ی کاربردی قصد دسترسی به آن را دارد. این منبع می‌تواند یک فایل داده یا یک پایگاه‌داده‌ی مبتنی بر DBMS باشد. در حالت مبتنی بر DBMS، اجزای زیر ممکن است در دسترسی به منبع داده نقش داشته باشند:

  • سیستم مدیریت پایگاه‌داده (DBMS)
  • سیستم‌عامل میزبان
  • شبکه و پروتکل ارتباطی (در صورت وجود)
  • داده‌های ذخیره‌شده

ارتباط SQL با توابع ODBC#

در ODBC، دستورات SQL و توابع API دو نقش متفاوت دارند:

  • دستورات SQL به‌صورت متن (String) نوشته می‌شوند و مشخص می‌کنند چه عملیاتی باید روی Data Source انجام شود.
  • در مقابل، توابع ODBC وظیفه‌ی مدیریت ارتباط، ارسال دستورات SQL، دریافت نتایج و آزادسازی منابع را بر عهده دارند.

بنابراین هر برنامه‌ای که بخواهد از ODBC استفاده کند، باید بخشی داشته باشد که توابع و APIهای ODBC را فراخوانی کند. این بخش بسته به نوع برنامه می‌تواند متفاوت باشد. به عنوان نمونه:

  • برنامه‌ی نوشته‌شده با C/C++: مستقیما توابع ODBC را فراخوانی می‌کند.
  • برنامه‌های .NET: می‌توانند از کلاس‌های System.Data.Odbc استفاده کنند که در نهایت با ODBC ارتباط برقرار می‌کنند.
  • SQL Server: خودش مستقیما ODBC را فراخوانی نمی‌کند. هنگام استفاده از Linked Server مبتنی بر ODBC، توابع ODBC در لایه‌ی ارتباطی SQL Server و در پشت صحنه فراخوانی می‌شوند. این کار از طریق MSDASQL و با تبدیل درخواست‌های OLE DB به ODBC انجام می‌شود و کاربر فقط با محیط نرم‌افزار یا دستورات SQL سروکار دارد.

ODBC در سیستم‌عامل‌ها#

برخلاف ویندوز که ODBC Driver Manager به‌صورت داخلی در سیستم‌عامل وجود دارد، در Linux و سایر سیستم‌های Unix معمولا باید یک Driver Manager جداگانه نصب شود.

  • Windows: Microsoft ODBC Driver Manager
  • Linux: unixODBC ، iODBC
  • macOS: unixODBC ، iODBC

🔔 ODBC یک استاندارد مستقل از سیستم‌عامل است. با این حال، باید Driver Manager و درایور متناسب با سیستم‌عامل و معماری برنامه نصب شده باشند.

ODBC در Windows#

در ویندوز، ابزاری به نام ODBC Data Source Administrator برای مدیریت تنظیمات ODBC در اختیار کاربران قرار دارد. این ابزار امکان مشاهده و مدیریت درایورهای ODBC نصب شده، تعریف و پیکربندی منابع داده (DSN3) و دسترسی به برخی تنظیمات مرتبط با ODBC را فراهم می‌کند.

فرض کنید برنامه‌ای قرار است به یک پایگاه‌داده‌ی SQL Server متصل شود. ابتدا باید درایور ODBC مربوط به SQL Server روی سیستم نصب شده باشد. سپس می‌توان با استفاده از این ابزار، تنظیمات اتصال به پایگاه‌داده را تعریف کرد تا برنامه بتواند از طریق ODBC به آن دسترسی پیدا کند. بدین‌سان، به‌جای اینکه اطلاعات اتصال به هر منبع داده در برنامه تعریف شود، می‌توان بخشی از تنظیمات را در سطح سیستم‌عامل مدیریت کرد.

آشنایی با زبانه‌ها#

زبانه کاربرد
1 User DSN تعریف منبع داده برای کاربر فعلی
2 System DSN تعریف منبع داده در سطح سیستم
3 File DSN ذخیره‌ی تنظیمات منبع داده در فایل
4 Drivers مشاهده‌ی درایورهای نصب‌شده
5 Tracing ثبت فراخوانی‌های ODBC برای عیب‌یابی
6 Connection Pooling استفاده‌ی مجدد از اتصال‌ها
7 About نمایش اطلاعات نسخه و اجزای ODBC

🔔 برای دسترسی به این ابزار، کافی است عبارت ODBC Data Sources را در منوی Start ویندوز جست‌وجو کنید.

User DSN
اطلاعات اتصال در محدوده‌ی حساب کاربری فعلی ویندوز ثبت می‌شود و فقط همان کاربر می‌تواند از آن استفاده کند و سایر کاربران ویندوز به آن دسترسی نخواهند داشت. محل ثبت:

Registry | HKEY_CURRENT_USER

System DSN
اطلاعات اتصال در سطح سیستم‌عامل ثبت می‌شود و محدود به یک کاربر خاص نیست. کاربران و سرویس‌هایی که مجوزهای لازم را داشته باشند، می‌توانند از آن استفاده کنند. محل ثبت:

Registry | HKEY_LOCAL_MACHINE

File DSN
اطلاعات اتصال به‌جای ثبت در تنظیمات ویندوز، در یک فایل با پسوند .dsn ذخیره می‌شود. این فایل را می‌توان به سیستم دیگری منتقل کرد یا در اختیار کاربران دیگر قرار داد. البته سیستم مقصد باید درایور مربوطه را نصب و به منبع داده دسترسی داشته باشد.

🔔 اعطای مجوز دسترسی به پایگاه‌داده باید به صورت جداگانه انجام شود.
یعنی تعریف DSN (نام منبع داده) به‌معنای ایجاد دسترسی به پایگاه‌داده نیست. DSN صرفا اطلاعات مورد نیاز برای شناسایی منبع داده و نحوه‌ی اتصال به آن را فراهم می‌کند.

🔔 اتصال بدون DSN

استفاده از DSN الزامی نیست.
در این حالت (DSN-less Connection) نیازی به تعریف منبع داده در ODBC Data Source نیست. برنامه می‌تواند اطلاعات اتصال، مانند نام درایور، سرور و پایگاه‌داده را مستقیما در قالب یک Connection String به Driver Manager ارسال کند.

Drivers
نصب درایور جدید معمولا از طریق اجرای بسته‌ی نصب (Installer) مربوط به آن انجام می‌شود. پس از نصب، در این زبانه فهرست درایورهای ODBC نصب شده روی سیستم به همراه مشخصات آن‌ها (نام، نسخه و …) نمایش داده می‌شود.

Tracing
برای ثبت و ضبط فراخوانی‌های ODBC در یک فایل گزارش (Log) استفاده می‌شود. این قابلیت هنگام عیب‌یابی مشکلات ارتباطی و بررسی نحوه‌ی تعامل برنامه با درایورهای ODBC کاربرد دارد.

Connection Pooling
این زبانه برای تنظیم و مدیریت قابلیت استفاده‌ی مجدد از اتصال‌های پایگاه‌داده (Connection Pooling) به کار می‌رود. با استفاده از این قابلیت، اتصال‌های برقرار شده می‌توانند پس از پایان استفاده، به جای بسته‌شدن، برای درخواست‌های بعدی نگهداری و مجددا استفاده شوند. این کار هزینه‌ی برقراری اتصال‌های جدید را کاهش می‌دهد.

About
این زبانه اطلاعاتی درباره‌ی نسخه و اجزای ODBC نصب‌شده روی سیستم نمایش می‌دهد.

تفاوت ODBC در ویندوزهای 32 و 64 بیتی#

در ویندوز 64 بیتی، دو نسخه‌ی 32 و 64 بیتی از ODBC Data Source Administrator وجود دارد. معماری برنامه تعیین می‌کند که از کدام نسخه و درایور استفاده کند.

  • برنامه‌ی 32 بیتی به درایور 32 بیتی نیاز دارد.
  • برنامه‌ی 64 بیتی به درایور 64 بیتی نیاز دارد.

مسیر دسترسی به نسخه‌ها:

  • 64-bit: C:\Windows\System32\
  • 32-bit: C:\Windows\SysWOW64\

نام پوشه‌ها گیج‌کننده است!!! پوشه‌ی System32 مربوط به نسخه‌ی 64 بیتی و پوشه‌ی SysWOW64 مربوط به نسخه‌ی 32 بیتی است.

🔔 هنگام نصب درایور و تعریف DSN باید معماری برنامه‌ی مصرف‌کننده را در نظر گرفت.
