مقدمه#

Null به معنای «هیچ، پوچ و …» است و یکی از شناخته‌شده‌ترین و بحث‌ برانگیزترین مفاهیم در پایگاه‌داده‌های رابطه‌ای است که از زمان معرفی آن تاکنون، موافقان و مخالفان زیادی داشته است. null یک حالت است نه یک مقدار، حالتی که معانی مختلفی می‌دهد و این نقطه‌ی شروع اختلافات شد.

تاریخچه#

مفهوم NULL در دنیای فناوری دو ریشه مستقل اما تقریبا هم‌زمان دارد:

  • ریشه سخت‌افزاری/حافظه‌ای (تونی هور Tony Hoare )
  • ریشه معنایی/اطلاعاتی (ادگار کاد) در دنیای Database

در سیستم‌های اولیه ذخیره‌سازی داده در دهه‌های ۱۹۶۰ و اوایل ۱۹۷۰ (پیش از مدل رابطه‌ای)، روش استانداردی برای نمایش داده‌های ناموجود وجود نداشت و هر سیستمی به شکل خاص خود با این مساله برخورد می‌کرد.

ادگار فرانک کاد ( Edgar F. Codd ) پدر علم دیتابیس‌های مدرن و یکی از محققین IBM، در سال ۱۹۷۰ مقاله مشهور خود درباره مدل رابطه‌ای را منتشر کرد که البته در آن چیزی به نام null وجود نداشت.

در حدود سال 1975 پژوهشگران IBM برای پیاده‌سازی مدل رابطه‌ای او، پروژه‌ای به نام « System R » را توسعه دادند. در این پروژه زبانی به نام SEQUEL 1 (که بعداً SQL 2 شد) ایجاد شد و مفهوم NULL را برای داده‌های ناقص در آن گنجاندند.

🔔 وجود منطق دو ارزشی (true, false) همراه با null باعث باگ‌های زیادی در System R شد.

ادگار کاد هرچند که در ابتدا از مخالفان رویکرد تیم IBM برای null بود اما در سال 1979 مساله «اطلاعات گمشده» (Missing Information) را مطرح کرد و مفهوم Null را به عنوان یک نشانگر (Marker) برای داده‌های از دست رفته یا ناموجود همراه با منطق ۳ ارزشی (True, False, Unknown) به صورت رسمی معرفی کرد، و در نهایت اولین استاندارد رسمی توسط ANSI و با نام ANSI SQL-86 در سال ۱۹۸۶ منتشر شد.

کاد در سال‌های بعد (1990) برای تفکیک بهتر، پیشنهاد کرد که دو نوع NULL داشته باشیم:

  • A-Mark (Applicable): این مقدار باید وجود داشته باشد ولی فعلاً نداریم. مثلا تلفن یک فرد، تعداد فرزندان یک کارمند و …
  • I-Mark (Inapplicable): این ویژگی برای این رکورد در حال حاضر معنا ندارد و نمی‌توان استفاده کرد. مثلا تعداد بارداری کاربر مرد!

💡 کاد عمداً از واژه Mark (نشان یا علامت) به جای (value) استفاده کرد که بگوید منظورش نشانگری (marker) برای تعیین وضعیت اطلاعات است نه مقدار آن.

💡 در بسیاری از پایگاه‌های داده، وضعیت NULL بودن ستون‌ها به ازای هر سطر در ساختاری به نام Null Bitmap ذخیره می‌شود. موتور دیتابیس با بررسی بیت مربوط به هر ستون تشخیص می‌دهد که مقدار آن NULL است، بدون آنکه نیازی به خواندن مقدار ذخیره‌ شده‌ی آن ستون داشته باشد.


تعریف NULL#

NULL نماینده‌ی نبود یا فقدان اطلاعات است. در واقع یک حالت و وضعیت (state) است نه یک مقدار (value)، و نشان می‌دهد هنوز مقداری ثبت نشده است (فیلد خالی است). در نتیجه از عملگرهای ریاضی که برای بررسی مقادیر استفاده می‌شد برای آن استفاده نشد و عملگرهای ویژه خود را دارد:

IS NULL
IS NOT NULL

select *
from employees
WHERE city is null

💡 IS NULL یک آزمون وضعیت است، نه یک مقایسه مقداری.

Null چه چیزهایی هست؟#

  • مقدار وجود دارد ولی نمی‌دانیم: مثلا گروه خونی کاربر که اعلام نشده
  • مقدار به وجود می‌آید اما در آینده: مانند تاریخ تحویل سفارش برای سفارشی که تکمیل نشده، تاریخ مرگ برای فرد زنده و … پس موقتا وجود ندارند (Temporarily Missing)
  • مقدار وجود دارد اما محرمانه است: مانند پنهان کردن حقوق مدیران. حتی ممکن است در جدول ثبت شده باشد، اما برای کاربران به صورت null نمایش داده شود.
  • مقدار وجود ندارد: مانند نام همسر برای کارمندی که هنوز ازدواج نکرده است، یا تعداد باردار شدن کارمند مرد و … برای این رکورد اصلا معنا و کاربرد ندارد (Inapplicable)؛ تا زمانی که ماهیت رکورد تغییر کند، مثلا مجرد تبدیل به متاهل بشود.

و موارد دیگری از این نوع که طبق نظر ادگار کاد، می‌توانند در دسته قابل استفاده اما نامعلوم یا دسته‌ی غیرقابل کاربرد قرار بگیرند.

🔔 مشکل همینجاست، ابهام معنایی! NULL چند مفهوم مختلف را در یک نماد واحد جمع کرده است. چگونه بفهمیم که منظور از null کدام یک از معانی گفته شده است؟

Null چه چیزهایی نیست؟#

  • صفر: یک مقدار عددی و معتبر
  • False یک مقدار منطقی معتبر
  • رشته خالی (Empty String) مثلا '' یا ""
  • فضای خالی (Blank String)یعنی رشته‌ای که طولش صفر نیست مثلا ' '

بدین ترتیب منطق دودویی معمول (True/False) برای برخورد با مقادیر null دیگر کافی نبود و SQL از منطق سه‌ ارزشی (Three-Valued Logic) استفاده کرد:
  • TRUE
  • FALSE
  • UNKNOWN: نمی‌دانیم نتیجه عبارت، درست است یا نادرست

فرض کنیم می‌خواهیم حقوق دو کارمند را با هم مقایسه کنیم. فیلد حقوق دو کارمند در حال حاضر خالی هستند. آیا می‌توان نتیجه گرفت که حقوق آن‌ها برابر، بزرگتر یا کوچکتر است؟ تنها می‌توانیم بگوییم که حقوق این دو فرد فعلا نامشخص است و نتیجه آن در منطق سه ارزشی SQL برابر با Unknown خواهد بود.

⚠️ در توابع تجمعی مثل SUM, AVG, COUNT(col_name) موارد نال نادیده گرفته می‌شوند.


انتقادها به null#

باک بنزین ماشین را تصور کنید:

  • اگر باک، بنزین داشته باشد نشان‌دهنده یک مقدار است (مثلاً 6۰ لیتر).
  • اما اگر باک کاملاً خالی باشد چه؟ می‌گوییم خالی! اما اینجا منظورمان از خالی صفر است نه اینکه ندانیم چه مقدار بنزین داریم. اینجاست که مفهوم فیلد خالی در دنیای دیتابیس با دنیای واقعی متفاوت و گیج کننده می‌شود! 😵

انتقادهای C. J. Date#

📣 سی‌جی دیت: وجود اطلاعات نامعلوم یک مساله واقعی است، اما NULL راه‌حل خوبی برای آن نیست.

Christopher J. Date از مخالفان جدی NULL محسوب می‌شود. چرا؟

  • ابهام معنایی به دلیل چند مفهومی بودن null
  • نقض قوانین منطقی: در ریاضی a = a همیشه درست (true) است اما در sql این منطق برقرار نیست و null = null (برابر) نخواهد بود.
  • پیچیدگی منطق سه‌ارزشی: ذهن انسان و ریاضیات کلاسیک به منطق دو ارزشی عادت کرده‌اند. منطق سه ارزشی باعث خطاهای پنهان می‌شود.

تصور کنیم 9 رکورد از کارمندان داریم. فیلد شهر برای 2 کارمند null، برای 4 کارمند شهر تهران و برای 3 کارمند شهرهای دیگر ثبت شده است. بر روی آن دو کوئری ساده اجرا می‌کنیم:

  • لیست کارمندانی که در تهران هستند؟ 4 رکورد
  • لیست کارمندانی که در تهران نیستند؟ انتظار جواب 5 را داریم (5 = 4 - 9) اما پاسخ 3 خواهد بود. جمع این دو لیست برابر با تعداد کل کارمندان نخواهد شد. زیرا رکوردهایی که شهرشان null است در هیچ یک از این لیست‌ها پدیدار نخواهند شد، و اینگونه نال برنامه‌نویسان را فریب خواهد داد. 😁
-- Total: 9
-- Result: 7
SELECT *
FROM employees
WHERE city = 'Tehran'
   OR city <> 'Tehran';

راه‌حل جایگزین «دیت» چه بود؟#

  • استفاده از مقادیر پیش‌فرضِ معنادار (Default Values): به جای null از مقادیر معنادار استفاده کنیم. مثلا استفاده از رشته N/A (not available) برای تلفن‌های اعلام نشده، یا ثبت تاریخ 1300/01/01 برای سفارش‌هایی که هنوز تاریخ تحویل ندارند.
  • تقسیم جدول اصلی به جدول‌های مجزا (Decomposition): برای ویژگی‌های اختیاری مثل اطلاعات همسر یا شماره تماس جداولی مجزا داشته باشیم تا برای افراد مجرد یا فاقد تلفن، اصلاً رکوردی ثبت نشود و در نتیجه هیچ نالی تولید نگردد.

Anti-Pattern#

💡 Anti-Pattern (ضد الگو)

به راه‌حلی گفته می‌شود که در نگاه اول خوب و منطقی به نظر می‌رسد، حتی ممکن است مدتی هم کار کند، اما در بلندمدت مشکلات بیشتری نسبت به مزایایش ایجاد می‌کند.

امروزه استفاده از N/A یا تاریخ 1300/01/01 در بسیاری از سیستم‌ها یک Anti-pattern محسوب می‌شود:

  • ابهام معنایی: آیا واقعا یک تاریخ است یا جایگزین نامشخص؟
  • کاهش کیفیت داده‌ها: اگر کاربر همین مقدار را وارد کند، چگونه با مقدار قراردادی، متمایزش کنیم؟
  • پیچیدگی پرس و جوها: به جای is null باید از شرط‌های اضافی استفاده کنیم.
  • احتمال خطای برنامه‌نویس: ممکن است برنامه‌نویس مقدار قراردادی را در فیلترها فراموش کند که لحاظ کند:
    • بخواهد کوچکترین تاریخ را مشاهده کند تحت تاثیر مقدار ساختگی قرار می‌گیرد (1300/01/01)
    • اگر میانگین زمان ارسال سفارش‌ها را حساب کند، بازهم مقدار جعلی دردسرساز خواهد بود
    • یا محاسبه سن افراد (کارمند 105 ساله👵👴)

و موارد دیگری از این دست.

💡 مگر اینکه این مقادیر واقعا بخشی از دامنه کسب و کار باشند نه برای فرار از نال. مثلا برای وضعیت تراکنش بانکی ثبت مقدار unknown تا دریافت نتیجه قطعی، مقدار جعلی نیست و مربوط به آن کسب و کار است.


بازگشت به منطق دو ارزشی#

ANSI در استاندارد SQL:1999 دستور جدیدی را معرفی کرد که در دیتابیس‌هایی مانند PostgreSQL و SQL Server 2022 تعبیه شده‌اند.

آیا دو عبارت با هم متفاوت هستند/نیستند؟ البته با منطق دو ارزشی

expression IS [NOT] DISTINCT FROM expression

این عملگرها به موتور دیتابیس می‌گویند که با NULL به عنوان یک «مقدار واقعی در زمان مقایسه» رفتار کند تا خروجی حتما True یا False شود. بدین ترتیب برنامه‌نویس دیگر مجبور نیست یک کوئری طولانی با چندین شرط OR بنویسد تا نال‌ها از زیر دستش در نروند.

در مثال زیر تفاوت = و IS NOT DISTINCT FROM را مشاهده می‌کنیم:


A B A = B A IS NOT DISTINCT FROM B
0 0 True True
0 1 False False
0 NULL Unknown False
NULL NULL Unknown True

برای راحتی فهم آن، چون null را به عنوان مقدار در نظر می‌گیرد، می‌توانیم بگوییم:

  • IS NOT DISTINCT FROM مانند = عمل می‌کند
  • IS DISTINCT FROM مانند <> عمل می‌کند
-- Total: 9
-- Tehran: 4
-- Result: 9 - 4 = 5

SELECT *
FROM employees
WHERE city IS DISTINCT FROM 'Tehran'

MSSQL#

در SQL Server سوییچی به نام ANSI_NULLS وجود دارد که به صورت پیش‌فرض مقدار آن On است.

  • ON: اگر عملگرهای مقایسه‌ای (=, <>, !=) استفاده شوند، نتیجه unknown خواهد شد و آن ردیف در نتایج نخواهد بود. باید از is null یا is not null استفاده شود.
  • OFF: با null مانند یک مقدار رفتار می‌شود.
WHERE Col = NULL
WHERE Col IS NOT NULL

در نسخه‌های اولیه که مبتنی بر Sybase بود امکان استفاده از این عملگرهای مقایسه‌ای بود. اما برای سازگاری با استاندارد ANSI SQL در دهه 90 تنظیمات ANSI مختلفی در MSSQL معرفی شدند تا برنامه‌نویسان امکان انتخاب بین رفتار قدیمی و استاندارد را داشته باشند. بدین ترتیب سازگاری با کدهای قدیمی (backwards compatibility) حفظ شد.

🚨 از SQL Server 2017 به بعد، ANSI_NULLS OFF منسوخ شده است (deprecated) و همیشه به صورت ON اعمال می‌شود. مایکروسافت توصیه می‌کند از OFF استفاده نکنید زیرا برخی از قابلیت‌ها مانند Index on Computed Columns دیگر کار نخواهند کرد.


Oracle#

در اوراکل رشته خالی (empty string) برای انواع variable characterها به عنوان null در نظر گرفته می‌شود، اما برای انواع char، به اندازه فضای گفته شده جا اشغال می‌شود. اگر کاراکتری ثبت نشود، این فضا با space پر می‌شود.

v1 char(10) 	:= '' ;  --> '          ' 
v2 varchar(100) := '';   --> null

سخن پایانی#

هرچند null مواقعی باعث سردرگمی برنامه‌نویسان می‌شود، اما به دلیل سادگی در پیاده‌سازی، به استاندارد غیرقابل‌حذف دیتابیس‌ها تبدیل شده است. در واقع null «شرّ ضروری» 😈 است که برای مدل‌سازی نواقص و نامعلومی‌های دنیای واقعی به آن نیاز داریم، به شرط آنکه با طراحی درست، بتوانیم خطاهای آن را مهار کنیم.
