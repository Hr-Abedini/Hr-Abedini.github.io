تعریف کلید#

کلید (Key) مجموعه‌ای از یک یا چند صفت (Attribute=Column) است که برای شناسایی یکتا، تمایز یا ایجاد ارتباط بین رکوردها (Tuple=Row) در یک رابطه (Relation=Table) به کار می‌رود.

کلید ابزاری است که با آن می‌توان:

  • یک رکورد را به‌طور یکتا شناسایی و بازیابی کرد.
  • بین جداول ارتباط برقرار کرد (از طریق کلید خارجی).
  • از ورود داده‌های تکراری جلوگیری کرد.
  • تمامیت داده‌ها (Data Integrity) را حفظ کرد.

🔔 در مدل رابطه‌ای ادگار اف. کاد (Edgar F. Codd) ، هر صفت دارای مقداری از دامنه (Domain) خود است و مفهوم NULL در نسخه اولیه این مدل وجود نداشت.
بنابراین، در تعریف کلاسیک کلید، به‌طور ضمنی فرض می‌شود که تمام صفات تشکیل ‌دهنده‌ی کلید دارای مقدار معتبر هستند؛ زیرا بدون مقدار، شناسایی یکتا امکان‌پذیر نیست. ( تاریخچه Null)
به همین دلیل، در تعاریف آکادمیک کلاسیک، قید NOT NULL معمولاً به‌صراحت ذکر نمی‌شود، بلکه بدیهی فرض می‌شود.  

براساس ساختار (تکی، چندتایی)#

1.تکی (Simple Key)#

کلیدی که تنها از یک ستون (صفت) تشکیل شده است.

2.مرکب/ترکیبی (Composite/Compound key)#

کلیدی که از دو یا چند ستون (صفت) تشکیل شده باشد.

  • همه کلیدها می‌توانند تکی یا مرکب باشند.
  • از نظر نظری، تعداد صفات تشکیل‌دهنده یک کلید محدودیتی ندارد، اما در عمل، هر سیستم مدیریت پایگاه داده (DBMS) ممکن است حداکثر تعداد ستون‌های مجاز در یک کلید را محدود کند.

🔔 امروزه در بیشتر کتاب‌ها، مقالات و مستندات، اصطلاحات Composite Key و Compound Key مترادف در نظر گرفته می‌شوند و هر دو به کلیدی اشاره دارند که از چند ستون تشکیل شده است، اما از دیدگاهی قدیمی‌تر منظور از Compound کلیدی بود که حداقل یکی از اجزای آن، خودش Foreign Key باشد، که امروزه این تعریف متداول نیست.

براساس منشا#

1. کلید طبیعی (Natural Key)#

کلیدی است که به ‌طور طبیعی برای شناسایی یک موجودیت وجود دارد و توسط همان کسب‌وکار ایجاد نشده است (منشا بیرونی دارد) مانند کد ملی، شماره گذرنامه، VIN خودرو، ISBN کتاب، ایمیل مشتری و …

  • توسط یک مرجع بیرونی یا استاندارد شناخته ‌شده تعریف شده است، نه توسط همان کسب‌وکاری که از آن استفاده می‌کند.
  • معنادار هستند.
  • برای هر موجودیت مقدار یکتایی دارند (unique).
  • نباید مقدار NULL داشته باشند.
  • با حذف کسب و کار، این شناسه همچنان وجود خواهد داشت.
  • بهتر است تا حد امکان ثابت باشد.
  • معمولاً تک ‌ستون است، هرچند می‌تواند مرکب نیز باشد.

2. کلید جانشین/مصنوعی (Surrogate/Artificial Key)#

صرفاً برای شناسایی رکورد ایجاد می‌شود و هیچ معنایی در دنیای واقعی (معنای کسب و کاری / تجاری) ندارد. مثل Auto-increment، GUID و …

  • برای ساخت یک شناسه یکتا برای هر رکورد ایجاد می‌شود.
  • بدون معنا است
  • معمولا به عنوان primary key انتخاب می‌شوند.
  • معمولا توسط سیستم تولید می‌شود.
  • پایدار، مستقل از تغییرات کسب‌ و کار و عملکرد بالا در joinها.

🔔 امروزه تقریباً همه منابع، Artificial Key و Surrogate Key را مترادف می‌دانند. هرچند در برخی منابع قدیمی‌تر بین این دو تمایز قائل می‌شدند:
برای مثال، در جدول ابتدا از کد ملی (Natural Key) به‌ عنوان کلید استفاده شده است، اما بعدها یک شناسه مانند GUID یا عدد خودافزا جایگزین آن می‌شود در این حالت surrogate key نام می‌گیرد؛ اما اگر از همان ابتدا از GUID استفاده می‌شد، Artificial Key نامیده می‌شد.

Surrogate Key: جایگزین یک کلید موجود (طبیعی/تجاری) می‌شد.
Artificial Key: از ابتدا به‌ عنوان کلید ایجاد می‌شد.

erDiagram CUSTOMER_SURROGATE { int CustomerId PK "Surrogate Key" string NationalCode UK "Natural Key قبلی" string Name string Phone } CUSTOMER_ARTIFICIAL { uuid CustomerId PK "Artificial Key" string NationalCode string Name string Phone }

3. کلید کسب‌وکار (Business Key)#

کلیدی است که قوانین کسب‌وکار آن را برای شناسایی یک موجودیت انتخاب کرده‌اند. مثل شماره سفارش، شماره فاکتور، شماره قرارداد، یا حتی کد ملی

بنابراین برای کلیدهای تجاری دو تعریف می‌توانیم داشته باشیم:

  1. Natural Key باشد مانند کد ملی
  2. شناسه‌ای باشد که خود سازمان برای فرایندهای کسب‌وکار ایجاد کرده است؛ مانند شماره فاکتور، شماره سفارش یا شماره پرسنلی

🔔 در Data Warehouse سیستم مبدأ، مرجع کسب‌وکار محسوب می‌شود.
بنابراین شناسه‌ای که در آن برای شناسایی یک موجودیت استفاده می‌شود، در DW به‌عنوان Business Key شناخته می‌شود، خواه یک Natural Key باشد یا یک Surrogate Key باشد.

براساس نقش#

1. اَبَر کلید (Super Key)#

مجموعه‌ای از یک یا چند صفت (ستون) در یک رابطه (جدول) است که هر رکورد (tuple) را به صورت یکتا (Unique) شناسایی می‌کند.

  • ممکن است شامل ستون‌های اضافی باشد، بنابراین کارآمدترین گزینه برای Primary Key نیست.
  • باید یکتا باشد (unique).
  • هیچ‌یک از صفات تشکیل‌دهنده آن نباید مقدار NULL داشته باشند.

مثال: جدولی با ستون‌های کد ملی، نام، نام خانوادگی داریم. طبق اصول نظریه مجموعه‌ها، برای n ستون، تعداد زیرمجموعه‌های ناتهی برابر با 2ⁿ−1 است، یعنی برای این مثال حداکثر 7 مجموعه خواهیم داشت که تنها ۴ مورد از این زیرمجموعه‌ها ابرکلید هستند:
  • اَبَر کلید هستند: {کد ملی}, {کد ملی، نام },{کد ملی، نام خانوادگی}, {کد ملی، نام، نام خانوادگی}
  • اَبَر کلید نیستند: {نام},{نام خانوادگی}, {نام، نام خانوادگی} چون ممکن است مقادیر تکراری داشته باشند.

اگر X یک ابرکلید باشد، هر مجموعه‌ای که شامل X باشد نیز یک ابرکلید است. در این مثال، چون {کد ملی} یک ابرکلید است، افزودن هر ستون دیگری به آن نیز همچنان یک ابرکلید ایجاد می‌کند.


2. کلید کاندید (Candidate Key)#

کلید کاندید (Candidate Key) ابرکلیدی است که مینیمال (Minimal) باشد؛ یعنی هیچ صفت غیرضروری در آن وجود نداشته باشد. به بیان دیگر، اگر از یک ابرکلید بتوان حتی یک ستون را حذف کرد و همچنان یکتا باقی بماند، آن ابرکلید، کلید کاندید نیست.

  • زیر مجموعه super key است.
  • هیچ ستون اضافه‌ای نداشته باشد.
  • ممکن است چند کلید کاندید در یک جدول وجود داشته باشد.
  • یکی از کلیدهای کاندید به عنوان primary key انتخاب می‌شود.

مینیمال بودن برای هر کلید به ‌صورت مستقل بررسی می‌شود و به سایر کلیدها ارتباطی ندارد. بنابراین، وجود یک Candidate Key کوچک‌تر (از نظر تعداد ستون) باعث نمی‌شود Candidate Keyهای دیگر رد شوند.


مثال: فرض کنیم جدولی با چهار ستون x, y, z, w داریم.
  1. x به تنهایی یکتاست.
  2. y, z با هم یکتا هستند.
  3. نه y به تنهایی یکتاست و نه z به تنهایی یکتا است.

بنابراین، هر دو مورد {x} و {y, z} کلید کاندید هستند. زیرا حذف هر ستون از آن‌ها باعث از بین رفتن خاصیت یکتایی می‌شود.


3. کلید اصلی (Primary Key)#

کلید اصلی (Primary Key) کلید کاندیدی است که برای شناسایی یکتای رکوردهای یک جدول انتخاب می‌شود.

  • از میان کلیدهای کاندید (Candidate Key) انتخاب می‌شود.
  • هر جدول فقط یک کلید اصلی دارد.

💡 توصیه می‌شود کلیدی به‌ عنوان Primary Key انتخاب شود که در طول زمان پایدار باشد و تغییر نکند. برای مثال، ممکن است شماره پرسنلی ابتدا با فرمت ۵ رقمی تعریف شود، اما با بزرگ شدن سازمان به ۸ رقم افزایش یابد. به همین دلیل، در بسیاری از سیستم‌ها استفاده از Surrogate Key به ‌عنوان Primary Key نسبت به Natural/Business Key ترجیح داده می‌شود.


4. کلید جایگزین (Alternate Key)#

هر کلید کاندیدی که به عنوان کلید اصلی انتخاب نشده باشد.

Alternate Key = Candidate Key - Primary Key

مانند کد ملی و ایمیل در یک جدول. کد ملی به عنوان کلید اصلی انتخاب می‌شود و ایمیل نیز در صورت یکتا بودن، یک Alternate Key و Natural Key است.

  • زیر مجموعه کلیدهای کاندید هستند.
  • معمولاً از میان Natural Key یاBusiness Key انتخاب می‌شوند..

🔔 در بعضی کتاب‌ها و مقالات قدیمی، به آن Secondary Key نیز گفته می‌شود. اما امروزه این کاربرد چندان رایج نیست و معمولا از اصطلاح Alternate Key استفاده می‌شود تا با مفهوم امروزی secondary key اشتباه گرفته نشود.

🔔 امروزه Secondary Key معمولاً به ستونی یا مجموعه‌ای از ستون‌ها گفته می‌شود که برای جستجو، فیلتر، مرتب‌سازی، گروه‌بندی یا دسترسی سریع‌تر به رکوردها به کار می‌روند. معمولاً برای بهبود کارایی، برای آن‌ها ایندکس ایجاد می‌شود.
Secondary Key الزاماً ویژگی‌های یک کلید (مانند یکتا بودن یا مینیمال بودن) را ندارد. برای مثال، نام خانوادگی مشتری می‌تواند یک Secondary Key باشد، هرچند ممکن است بین چندین مشتری مشترک و تکراری باشد.

5. کلید خارجی (Foreign Key)#

کلید خارجی (Foreign Key) قیدی (Constraint) است که بین دو جدول رابطه برقرار می‌کند و تضمین می‌کند مقدار یک یا چند ستون در جدول فرزند (Child) فقط به مقادیری اشاره کند که در جدول والد (Parent) وجود دارند.

Order.OrderID → Customer.CustomerID

erDiagram direction LR Customer { int CustomerID PK string Name } Order { int OrderID PK int CustomerID FK date OrderDate } Customer ||--o{ Order : ""

  • به Primary Key یا Unique Key جدول مرجع ارجاع می‌دهد.
  • از ارجاع به رکوردهای نامعتبر جلوگیری می‌کند (Referential Integrity).
  • می‌تواند مقدار تکراری داشته باشد، اما مقدار آن باید در جدول مرجع وجود داشته باشد.
  • می‌تواند مقدار NULL داشته باشد.

⚠️ نام Foreign Key ممکن است گمراه‌ کننده باشد. با وجود اینکه «کلید» نامیده می‌شود، در جدول فرزند معمولاً یک کلید واقعی نیست. زیرا هم می‌تواند مقدار NULL داشته باشد و هم مقادیر تکراری. واژه Foreign فقط نشان می‌دهد که این ستون به کلیدی در جدول مرجع اشاره می‌کند.


6.کلید یکتا (Unique Key)#

یک قید (Constraint) در پایگاه داده است که تضمین می‌کند هیچ دو رکوردی مقدار یکسانی برای یک ستون یا مجموعه‌ای از ستون‌ها نداشته باشند.

  • یک جدول می‌تواند چندین Unique Key داشته باشد.
  • می‌تواند به‌عنوان مرجع Foreign Key استفاده شود.
  • نحوه برخورد با مقدار NULL به DBMS و تا حدی به استاندارد SQL بستگی دارد.
    • SQL Server: تنها یک Null برای Unique Constraint قبول می‌کند
    • Oracle: می‌تواند چندین Null داشته باشد.

Unique بیش از آنکه یک نوع کلید جدید باشد، روشی برای اعمال یکتایی روی داده‌ها و پیاده‌سازی Candidate Key یا Alternate Key است.

Pasport.OwnerNationalCode → Person.NationalCode
erDiagram direction LR Person { int PersonId PK string NationalCode UK string FullName } Passport { int PassportId PK string OwnerNationalCode FK string PassportNo UK } Person ||--o{ Passport : ""

⚠️ نام Unique Key ممکن است گمراه‌کننده باشد. از دیدگاه مدل رابطه‌ای، کلید باید برای همه رکوردها مقدار معتبر داشته باشد، در حالی که UNIQUE در بسیاری از DBMSها اجازه مقدار NULL را می‌دهد. بنابراین UNIQUE در اصل یک Constraint برای اعمال یکتایی است و معمولاً برای پیاده‌سازی Candidate Key یا Alternate Key به کار می‌رود، نه یک نوع کلید مستقل.
